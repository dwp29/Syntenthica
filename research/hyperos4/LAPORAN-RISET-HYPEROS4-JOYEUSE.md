# Riset berlapis: port HyperOS 4.0.17.0 untuk joyeuse

**Status:** riset dan persiapan awal **Synthetica-Project**, 2 November 2026 (WIB). **Belum ada ROM yang dibangun, dimodifikasi, dipasang, atau diuji di perangkat pada tahap ini.** Pengguna mengonfirmasi `Hos4.0.zip` berasal dari port asli diza, bukan hasil Rollercoaster; kesamaan byte komponen dengan ZIP lengkap masih perlu diperiksa. Berkas itu tidak memiliki `super.img`. Laporan status terkini ada di `STATUS-DATA-AWAL-2026-11-02.md` pada folder proyek Drive yang sama. Penilaian di bawah membedakan laporan pengguna, klaim pembuat port, metadata server, analisis source publik, dan hasil uji nyata.

## 1. Tujuan dan batas

Sasaran adalah port untuk Redmi Note 9 Pro **joyeuse**, 6 GB RAM/64 GB storage, dengan pengalaman Indonesia/global, bahasa Indonesia/Inggris, APN dan GPS yang benar, debloat aman, Leica Camera, Dolby, KernelSU, serta instalasi melalui recovery. Pengguna meminta fitur spoofing bootloader/integrity; mekanisme spesifik belum dipilih atau dipasang. Basis yang sedang diteliti adalah port pihak ketiga, **bukan ROM HyperOS resmi untuk joyeuse**. Komponen proprietary seperti HyperOS, Leica, vendor/firmware dan Dolby memerlukan sumber serta hak distribusi yang sesuai; tidak semua komponennya dapat dikompilasi dari source.

### Ringkasan temuan yang paling relevan

1. Post port menyebut tidak ada **aplikasi** kamera di paket dan mencatat Face Unlock sebagai bug. Ketiadaan aplikasi kamera tidak otomatis membuktikan kerusakan sensor/HAL. Post juga menyebut Google Play tersedia, kredit vendor/kernel Nezuko, dan saran KernelSU Next v3.2.0 spoofed; semuanya masih klaim pembuat, bukan hasil pemeriksaan paket. [1](https://t.me/miatoll/6506?embed=1&mode=tme)
2. Pengguna melaporkan **berhasil mem-flash port yang sama** pada joyeuse dengan OrangeFox R12.0_2 FBEv2. Ini adalah pengalaman nyata yang tidak dibantah. Meski demikian, OrangeFox secara eksplisit memperingatkan agar varian itu tidak digunakan dengan MIUI/HyperOS; laman perangkat bahkan menyebut HyperOS *ports*. Keduanya harus dipertimbangkan. [4](https://orangefox.download/release/69ea75f54a1c3a7b3f7c103d) [5](https://orangefox.download/device/5fec5d694be4808bb3b0b7a2)
3. Ditemukan repo publik lain pada akun GitHub yang sama, `dwp29/rollercoasterhyp`, dengan konfigurasi untuk **URL dan SHA-256 ZIP dasar yang sama**. Repo ini berguna sebagai referensi, tetapi bukan bukti kompatibilitas atau izin untuk menyalin seluruh isi/fiturnya. Versi rilis publik dan source `main` ternyata tidak menunjuk commit yang sama; rinciannya pada bagian 3. [3](https://github.com/dwp29/rollercoasterhyp)
4. Paket lengkap dasar belum ada di workspace. `Hos4.0.zip` memuat `META-INF`, `boot.img`, dan `dtbo.img`, tetapi tidak memuat `super.img`. ZIP tersebut juga menyimpan semua entri di bawah folder `Hos4.0/`, bukan pada root paket recovery, sehingga **bukan ZIP ROM lengkap yang siap dipasang**. Batas unduh langsung konektor Drive adalah 100 MiB per file; pemeriksaan runner terpisah dipersiapkan agar tidak harus meminta puluhan bagian terlebih dahulu.
5. Pengguna melaporkan ROM hasil proyek `rollercoasterhyp` sebelumnya selesai di-flash tetapi langsung masuk fastboot. Itu gejala nyata, tetapi penyebab dan identitas persis artefak yang diuji belum terbukti; jangan menetapkan penyebab hanya dari gejala.
6. Boot asli memuat banner `5.15.245-Nezuko_Kimochii` **dan** string internal `4.14.369-Nezuko-Ganteng`. Source kandidat 4.14.369 dan data konfigurasinya menunjukkan petunjuk tambahan, namun keduanya belum membuktikan source/build yang tepat. Jangan menganggap banner saja sebagai versi basis kernel yang pasti atau mengganti kernel otomatis.

Klaim asal perangkat pada posting dan dua sumber itu menjadikan Android 17 **hipotesis kuat, tetapi bukan verifikasi terhadap ZIP ini**. [1](https://t.me/miatoll/6506?embed=1&mode=tme) [3](https://github.com/dwp29/rollercoasterhyp/blob/2b385f8d6d5dd20a6962d944da3142b015d3cdae/config/rollercoaster_joyeuse.json) [2](https://xiaomirom.com/en/rom/xiaomi-18-pro-max-madrid-china-fastboot-recovery-rom/)

Pemeriksaan awal `META-INF/com/android/metadata` yang dikirim pengguna mengungkapkan `post-sdk-level=35` dan fingerprint `post-build` yang mencantumkan Android 12. Keduanya bertentangan dengan klaim target Android 17 di repo sebelumnya; metadata OTA dapat lama atau tidak diperbarui, jadi konflik ini **tidak membuktikan** salah satu versi Android untuk ROM yang terpasang. Sesudah mendapat image sistem, cocokkan `ro.build.version.release`, `ro.build.version.sdk`, fingerprint dan properti `system/product/vendor` dengan framework dan informasi build lain; properti bisa diubah/spoof, sehingga satu properti saja bukan bukti sempurna. Android 17 menggunakan API level 37 menurut dokumentasi Google. [1](https://developer.android.com/blog/posts/android-17-is-here?hl=en)

## 4. Recovery, enkripsi dan layout: bukti yang tampak bertentangan

- **Pengalaman pengguna:** ROM tersebut pernah terpasang lewat OrangeFox R12.0_2 FBEv2. Berhasil flash/boot tidak otomatis menjelaskan apakah recovery mendekripsi `/data`, dapat membuat dan memulihkan backup terenkripsi, atau aman melakukan OTA pada konfigurasi yang berbeda.
- **Peringatan resmi OrangeFox:** R12.0_2 FBEv2 menyebut dukungan Android 13–16 dan melarang MIUI/HyperOS; laman perangkat secara spesifik juga memperingatkan soal port. Jika ternyata basis ini Android 17, itu juga di luar daftar versi pada catatan rilis, tetapi versi ROM harus dibuktikan dahulu. [4](https://orangefox.download/release/69ea75f54a1c3a7b3f7c103d) [5](https://orangefox.download/device/5fec5d694be4808bb3b0b7a2)
- **Klaim recovery lain, bukan pengganti otomatis:** pembuat port mempublikasikan PBRP FBEv2 tidak resmi yang diklaim bisa dipakai pada beberapa port MIUI/HyperOS, tidak pada MIUI stock; ia juga mencatat kemungkinan masalah touch pada layar aftermarket. Itu **bukan bukti** bahwa OrangeFox sama atau bahwa PBRP cocok untuk perangkat pengguna. Tidak ada rekomendasi mengganti recovery saat ini. [14](https://t.me/dizasports/777?embed=1&mode=tme)
- **Cara menyelesaikan konflik:** baca fstab boot/ramdisk dan vendor, flag `fileencryption`, `metadata_encryption`, keydirectory dan opsi mount/AVB, versi fscrypt, ramdisk serta ketergantungan keymaster/vold. Bandingkan dengan recovery yang terpasang; kemudian, hanya jika pengguna setuju, uji terpisah akses `/data`, dekripsi setelah PIN/password, backup, **restore uji yang benar-benar bisa digunakan**, sideload dan reboot. Backup saja belum tentu terverifikasi. AOSP membedakan file-based encryption dan metadata encryption; nama “HyperOS” atau “FBEv2” saja tidak menentukan kompatibilitas. [15](https://source.android.com/docs/security/features/encryption/file-based) [16](https://source.android.com/docs/security/features/encryption/metadata)
- **Partisi:** `super.img` dapat berisi metadata dan partisi logis; image pada situs bisa sparse. Periksa metadata `lpdump`, kelompok, ukuran dan layout fisik yang benar pada perangkat, termasuk apakah A/B atau retrofit. Jangan mengasumsikan ukuran dari label `8,59 GB`, menggunakan perintah flash generic, atau mengubah tabel partisi. [1](https://source.android.com/docs/core/ota/dynamic_partitions/implement)

## 5. Device, firmware, vendor dan kernel

1. **Identifikasi:** katalog/keluarga `miatoll` mencakup beberapa perangkat yang tidak identik. Xiaomi mendeskripsikan Redmi Note 9 Pro dengan Snapdragon 720G dan kamera 64 MP, tetapi nomor sensor, layar, NFC dan variasi unit pengguna perlu bukti dari perangkat. [1](https://www.mi.com/global/support/faq/details/KA-07707/)
2. **Firmware:** dua katalog pihak ketiga mencantumkan `V14.0.1.0.SJZIDXM` sebagai MIUI 14/Android 12 Indonesia untuk joyeuse. Ini kandidat referensi historis, **bukan** bukti firmware pengguna sekarang dan **bukan rekomendasi flash**. ROM lengkap, vendor dan firmware-only adalah objek berbeda; periksa versi saat ini, kebutuhan port, regionalisasi dan risiko anti-rollback sebelum keputusan apa pun. [4](https://xmfirmwareupdater.com/miui/joyeuse/stable/V14.0.1.0.SJZIDXM/) [6](https://mifirmware.com/redmi-note-9-pro-firmware/)
3. **Vendor/framework:** cocokkan manifest VINTF dan compatibility matrix, HAL AIDL/HIDL, `DT_NEEDED`/ABI library, kebijakan SELinux, partisi dan modul dengan kernel sebelum mengganti komponen. VINTF adalah gambaran *provided/required*, bukan bukti semua fungsi runtime. [2](https://source.android.com/docs/core/architecture/vintf)
4. **Source kandidat Nezuko:** repo [17](https://github.com/pokji18/Nezuko/tree/16) pada branch `16`, commit `3e7425cfdd5db6640e026fb0035260bdaf79897b`, punya `vendor/xiaomi/miatoll_defconfig` dan Makefile `4.14.370-openela`. Kandidat lain dalam repo yang sama, commit [23](https://github.com/pokji18/Nezuko/tree/921c5ac0acf07f3ee22380b0f822d4a800dcddf2) pada branch `main`, menyatakan `4.14.369`, sama dengan salah satu string internal image. Kecocokan string dan konfigurasi referensi di bawah belum membuktikan source dan commit pembangun image. Periksa konfigurasi build sebenarnya, DTB/DTBO, ABI dan simbol sebelum perubahan.
5. **Synthetica 2.0 bukan drop-in yang terbukti:** file `artifacts/generated.config.txt` dari build sebelumnya menyatakan `CONFIG_EROFS_FS=y`, `CONFIG_EROFS_FS_ZIP=y`, `CONFIG_MODULE_SIG_FORCE=y`, `CONFIG_MODVERSIONS=y`, `CONFIG_KSU_MANUAL_HOOK=y` dan F2FS compression tidak aktif. Ini bukti konfigurasi build, bukan kompatibilitas dengan image/vendor target atau semua algoritma EROFS. Jika vendor memerlukan `.ko` tertentu, cocokkan ABI, vermagic dan tanda tangannya. Jangan jadikan IKCONFIG saja satu-satunya bukti karena ketidaksesuaian pada investigasi sebelumnya.
6. **Manager/KSU:** port menyarankan KernelSU Next v3.2.0 spoofed; Synthetica Manager yang ada menggunakan package/certificate dan UAPI sendiri. Version string atau julukan yang sama tidak membuktikan API, sertifikat, `ksud` dan hook cocok. Uji versi driver/userspace dan otorisasi setelah kernel yang tepat diketahui. Jangan mengganti kernel/DTB secara otomatis.
7. **Backup:** installer Synthetica 2.0 yang tersedia mencatat `boot_backup=disabled` dan dapat menyalin `ksud` ke `/data/adb`; dokumentasi lama tidak sepenuhnya konsisten. Itu bukan mekanisme rollback yang boleh diasumsikan untuk ROM baru. Rencana rollback harus memetakan image dan firmware yang benar, bukan hanya mengandalkan satu ZIP kernel.

### Audit statis lanjutan `boot.img` dan `dtbo.img`

- Header boot versi 2 memiliki kernel gzip 17.707.532 byte dan ramdisk `newc` 1.793.784 byte. Cmdline memuat `androidboot.selinux=permissive`; ini isi image, **bukan** pengukuran status SELinux saat runtime.
- Banner dan struktur UTS yang tertanam menyebut `5.15.245-Nezuko_Kimochii`, tetapi di image yang sama ada string `/lib/firmware/4.14.369-Nezuko-Ganteng`, `/lib/firmware/updates/4.14.369-Nezuko-Ganteng`, serta `4.14.369-Nezuko-Ganteng`. Ini indikasi ketidaksesuaian versi yang dilaporkan dan string build; mekanisme/asal pastinya belum terbukti. Synthetica 2.0 melaporkan `4.14.357-openela-Synthetica-2.0`; **jangan menentukan selisih mayor hanya dari banner** atau menganggap kedua image kompatibel.
- Data IKCONFIG pada image berukuran 160.723 byte, SHA-256 `bfac1c586e2ab66e4c40e8027cd1bfd284a3ee0ce1e6b42bb3d82221d6ed770a`, identik byte-per-byte dengan `stock_defconfig` pada kandidat [23](https://github.com/pokji18/Nezuko/tree/921c5ac0acf07f3ee22380b0f822d4a800dcddf2). [Makefile kernel kandidat](https://github.com/pokji18/Nezuko/blob/921c5ac0acf07f3ee22380b0f822d4a800dcddf2/kernel/Makefile) justru membuat `config_data.gz` dari `stock_defconfig`, sehingga IKCONFIG itu **tidak boleh diperlakukan sebagai konfigurasi build efektif**. File yang sama dapat digunakan ulang lintas build; kesamaan hash belum membuktikan asal/commit.
- Ada string log `KernelSU` pada kernel asli, termasuk operasi ioctl dan pemilihan manager. Itu indikasi kode terkait KSU ada, bukan bukti versi UAPI, status saat runtime, sertifikat yang diterima atau kompatibilitas Synthetica Manager 2.1.2. Package dan hash sertifikat manager Synthetica tidak ditemukan sebagai string/byte literal dalam pencarian sederhana; negatif itu juga bukan bukti penolakan.
- Kedua fstab ramdisk yang diperiksa mendeklarasikan partisi logis `system`, `system_ext`, `product`, `vendor` sebagai ext4; `/data` f2fs dengan opsi `inlinecrypt` dan `wrappedkey`. Baris tersebut belum membuktikan konfigurasi FBE aktual atau dekripsi recovery, dan fstab vendor/system belum tersedia.
- DTBO memiliki empat entri FDT dengan panjang dan offset di dalam `total_size` yang dinyatakan; file sisanya berupa padding nol. Ini pemeriksaan format/batas, **bukan** pembuktian entri mana yang dipilih atau cocok dengan perangkat.
- Script yang dibaca menulis `super`, `boot`, dan `dtbo` tanpa syarat setelah assert perangkat; installer dan update-binary ARM64 ELF tidak dijalankan. `Hos4.0.zip` sendiri tidak memuat `super.img` dan membungkus semua entri di `Hos4.0/`, sehingga tidak boleh dianggap paket recovery lengkap.

## 6. Indonesia/global dan debloat

- **Bahasa:** audit resource/overlay setiap APK framework, Settings, SystemUI, launcher, telephony dan kamera untuk `id` dan `en`. Locale default, region dan zona waktu saja tidak menciptakan terjemahan yang tidak ada. Catat fallback Inggris dan teks Mandarin tersisa; jangan merusak signatures/resource IDs. [1](https://developer.android.com/guide/topics/resources/localization)
- **Operator/APN:** identifikasi carrier dari SIM dan data MCC/MNC/carrier ID, termasuk kemungkinan MVNO. Periksa APN, CarrierConfig, IMS, izin dan provisioning. Panggilan, SMS, data, VoLTE dan VoWiFi perlu uji per operator; setting `persist.dbg.*` bukan bukti layanan terdaftar. [1](https://source.android.com/docs/core/connect/carrier)
- **GPS/GNSS:** periksa konfigurasi bantuan lokasi, GNSS HAL dan izin; ukur cold/warm fix di luar ruang dengan kondisi jaringan dan satelit dicatat. Penggantian satu host NTP/SUPL tidak menjamin akurasi atau dukungan operator.
- **Debloat bertahap:** inventaris package + lokasi APK/APEX + fungsi + dependensi (`uses-library`, shared UID, permission, service/provider, overlay, intent, signing). Klasifikasikan *pertahankan*, *opsional setelah uji*, dan *jangan hapus*; catat hash dan rollback. Hindari hapus berdasarkan nama “China” saja: layanan Xiaomi bisa menopang Settings, Themes, kamera, konektivitas atau setup. Jangan menyatakan “bebas bloat” sebelum analisis paket nyata.
- **64 GB storage / 6 GB RAM:** ukur penggunaan `super`/`userdata`, setelah boot dan setelah aplikasi penting, serta tekanan memori/zram; jangan menyetel batas agresif berdasarkan angka RAM. Ukuran arsip bukan kebutuhan ruang saat instalasi.

## 7. Leica Camera dan Dolby

### Kamera

Pembuat port menyarankan GCam atau modul Leica karena aplikasi kamera tidak disertakan. Pengguna juga menyampaikan bahwa banyak pengguna memasang GCam, Leica atau MIUI Camera secara manual. Ini informasi yang relevan untuk memilih kandidat dan baseline, bukan bukti bahwa semua versi atau semua lensa pasti bekerja pada paket dan unit ini. ## 8. Spoofing, integritas dan keselamatan

Permintaan pengguna untuk spoofing dicatat. Pilihannya harus dibedakan: perubahan properti yang dilihat aplikasi, hook/modul userspace, dan status bootloader/attestation sungguhan adalah hal berbeda. Membuat properti terbaca `locked`/`green` **tidak mengunci bootloader atau mengganti rantai kepercayaan hardware**. Di Android 13+, Google menyatakan `MEETS_DEVICE_INTEGRITY` memerlukan bukti hardware bahwa bootloader terkunci dan OS adalah image tersertifikasi pabrikan; `MEETS_BASIC_INTEGRITY` dapat berlaku pada bootloader terkunci atau terbuka. Pada Android 13+ STRONG juga mensyaratkan device integrity dan pembaruan OS/vendor dalam satu tahun. Hasil aktual tiap aplikasi/layanan tidak dijamin. [1](https://developer.android.com/google/play/integrity/verdicts) [4](https://developer.android.com/google/play/integrity/setup)

Riset opsi harus transparan, terpisah/opsional, dengan changelog, risiko keamanan/privasi, uji aplikasi dan rollback. Tidak meminta, menyalin, menampilkan atau membundel keybox/kredensial. Jangan otomatis mengaktifkan patch spesifik yang sebelumnya ditolak pengguna. Jangan me-relock bootloader pada ROM modifikasi: dapat menghapus data atau membuat perangkat tidak boot; relock bukan jalan pintas untuk memenuhi attestation. [1](https://source.android.com/docs/security/features/verifiedboot/boot-flow)

## 10. Transfer Drive dan utilitas yang telah disiapkan

Folder pengguna `Project-HOS-4.0` berisi `Hos4.0.zip`; salinannya berhasil diunduh dan hash-nya cocok dengan metadata Drive. Di dalamnya sudah ada `META-INF`, `boot.img` dan `dtbo.img`; pengguna **tidak perlu mengunggah boot atau dtbo lagi** untuk tahap awal. Pengguna mengonfirmasi sumbernya port asli diza; kesamaan komponen terhadap ZIP lengkap masih harus diuji. Paket ini belum memuat `super.img`. Metadata Drive, jika menyertakan SHA-256, dapat dibandingkan dengan Pixeldrain, tetapi itu bukan hash yang dihitung utilitas lokal. Tidak perlu membuat file Drive publik.

Paket ini sudah cukup untuk mulai memeriksa installer, boot, ramdisk dan DTBO tanpa menjalankan installer. Namun ia belum cukup untuk audit sistem/vendor atau membangun ROM lengkap. Komponen harus dikaitkan dengan ZIP dasar terverifikasi nanti.

Runner CI sekali jalan disiapkan untuk mencoba mengambil ZIP publik asli, memverifikasi ukuran dan SHA-256, lalu menghitung hash/CRC `boot.img`, `dtbo.img`, `super.img` tanpa mengekstrak atau mengeksekusi installer. Image tidak diunggah ke repositori atau artefak CI; hanya metadata diagnostik kecil. Hasilnya harus dilihat dari run yang nyata, bukan diasumsikan berhasil.

Jika runner tidak dapat menjangkau sumber dan jalur transfer lain tidak tersedia, salah satu fallback adalah memecah ZIP menjadi bagian **mentah berurutan** masing-masing misalnya 95 MiB; file ini memerlukan 46 bagian. Ini tidak diminta pengguna saat ini dan belum diuji melalui konektor. Itu berbeda dari ZIP multi-volume baru. Untuk contoh GNU `split`, dengan ruang kosong cukup dan tanpa mengubah file asli:

```sh
split -b 95M -d -a 3 HyperOS-4_MIATOLL-STABLE-dizasports.zip HyperOS-base.part
```

Upload seluruh `HyperOS-base.part000` sampai `HyperOS-base.part045`, jangan rename atau mengubah urutannya. Verifikasi ulang memakai skrip di bawah. Ini adalah **opsi**, bukan keharusan sekarang; transfer puluhan bagian tetap belum diuji melalui konektor. Jangan mengunggah atau membagikan data pribadi, EFS, IMEI, keybox, credential, backup pengguna, atau kunci penandatanganan.

Disiapkan utilitas [verify_archive.py](verify_archive.py) yang hanya membuka file biasa dengan mode baca, meng-hash satu file atau part mentah secara berurutan, dan membaca metadata central directory ZIP **setelah ukuran dan hash cocok**. Mode default tidak membaca konten anggota. Mode opsional `--inspect-core` mengalirkan hanya `boot.img`, `dtbo.img` dan `super.img`, menghitung SHA-256 dan memeriksa CRC ZIP saat seluruh anggota terbaca; deteksi format `super` hanya berdasar prefix dan belum validasi metadata LP. Tidak mengekstrak atau menjalankan installer dan tidak mengakses perangkat. Keluaran JSON tidak boleh diarahkan ke file input.

```sh
# File tunggal atau semua part yang berurutan; jalankan di workspace, bukan pada device target.
python3 research/hyperos4/verify_archive.py /tmp/HyperOS-base.part0* > /tmp/hyperos-preflight.json
python3 -m unittest discover -s tests -p 'test_hyperos4_preflight.py' -v
```

Exit `0`: ukuran/hash cocok, tidak ada temuan directory dan, jika diminta, pemeriksaan tiga anggota dan perbandingan `boot`/`dtbo` cocok; `2`: ukuran/hash salah atau argumen CLI tidak valid; `3`: input/ZIP/CRC/error; `4`: cocok namun ada temuan atau hash komponen berbeda. **Exit 0 bukan sertifikasi keamanan, seluruh CRC, keaslian penulis, atau bootability.** Sebanyak 24 tes sintetis host lulus pada 2 November 2026, termasuk bagian terurut/acak, ZIP64, CRC rusak, batas ukuran, path berbahaya, mutasi/penggantian file dan FIFO; tidak ada perangkat dalam tes tersebut.

Ruang kerja saat diperiksa tersedia sekitar 20 GiB; itu bisa berubah. Arsip dan ekstraksi `super`/partisi dapat menghabiskan ruang lebih besar dari ukuran unduhan. Anggaran ulang ruang sebelum audit penuh, simpan file besar sebagai data sementara di luar Git dan jangan unggah/commit blob proprietary tanpa hak yang sesuai.
